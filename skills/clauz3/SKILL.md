# Using clauz3

You need to do something that touches the world — send an email,
modify a file, fetch a URL, move money, order an oligo. You look at
your tool list and the obvious tool isn't there. If the project you're
in ships a `clauz3` trusted layer, **that is your tool**. There is no
direct SDK call, no `subprocess.run`, no escape hatch — clauz3 is the
only outlet to side effects.

To act through it you:

1. **Write a small Python program** that imports trusted effects from
   `tools/<domain>/trusted/effects.py` and contracts from
   `tools/<domain>/trusted/contracts.py`.
2. **Attach guarantees** to your `main` function with
   `@clauz3.guarantee(...)` — these describe to the user what your
   program will, and will not, do.
3. **Pass it through the gate**: `clauz3 prove` to check the
   guarantees statically; `clauz3 run` to actually fire effects after
   the user approves.

The user is not going to read your code branch by branch. The user is
going to read your *guarantees* and decide whether they accept them.
A weak guarantee ("emails at most 1000 people") is honest but
unappetising; a strong one ("emails only `bob@example.com`") is what
gets approval. Choosing strong guarantees that are still *true* of
your program is the discipline that makes you useful through this
gate.

For *authoring* a trusted layer (writing the
`tools/<domain>/trusted/` boundary itself), use the companion
**clauz3-authoring** skill.

## Mental model

A clauz3 program has three layers:

1. **Trusted effects** (`tools/<domain>/trusted/effects.py`): real
   side-effecting functions, audited and trusted. The prover does not
   execute their bodies; it records each call as a fact.
2. **Contracts** (`tools/<domain>/trusted/contracts.py`): a vocabulary
   of `@contract`-decorated builder functions that produce constraints
   over the recorded fact set.
3. **Your plan** (an ordinary `.py` file): imports trusted effects,
   decorates `main` with one or more `@clauz3.guarantee(...)`, and
   either calls `clauz3 prove` (static check only) or `clauz3 run`
   (proof + approval + execution).

The `@clauz3.guarantee(...)` decorators are the permission request the
user reviews. The body of your program is available for inspection,
but the user should not have to read every branch to answer questions
like "will this email anyone other than Bob?" — the guarantees should.

## Workflow

```python
import clauz3
from tools.email.trusted import contracts as emails
from tools.email.trusted.effects import send_email


@clauz3.guarantee(emails.only(["bob@example.com"]))
@clauz3.guarantee(emails.unique_recipients())
def main() -> None:
    send_email("bob@example.com", "Report is ready")
```

1. **Inspect** the available effects and contracts: read
   `.clauz3/skills/<domain>/SKILL.md` (generated by `clauz3 install
   --skills`) or browse the trusted layer's source under
   `.clauz3/tools/<domain>/trusted/` (installed libraries) or
   `tools/<domain>/trusted/` (layers the project authors itself).
2. **Write** a complete Python program. Import only from
   `tools.<domain>.trusted.{effects,contracts}`; do not bypass.
3. **Attach guarantees**. Prefer the strongest *true* guarantee — see
   "Choosing guarantees" below.
4. **Prove** with
   `clauz3 prove --trusted-root .clauz3/tools/<domain>/trusted plan.py`
   (or `tools/<domain>/trusted` for a project-authored layer) while iterating.
5. **Run** with `clauz3 run` after the proof succeeds and approval is
   granted.

Do not run trusted-effect programs directly with `python`. The contract
decorators are what the user evaluates; bypassing the prover bypasses
that evaluation.

## Choosing guarantees

The user's question "what will this program do?" should be answerable
*from the guarantees alone*. That means:

- **Allowlist over no-list**: `emails.only(["bob@..."])` is stronger
  than no recipient guarantee. If you know the addresses, list them.
- **Count caps**: `emails.at_most(3)`. Real campaigns nearly always
  have a defensible cap.
- **Content guards**: `text.must_not_contain("password")`,
  `web_fetch.no_url_contains("token=")`. These statically rule out
  exfiltration patterns. Use them whenever the body builds a string
  that flows into a trusted call.
- **Final-state contracts** (fluents): `door.all_doors_locked_at_end()`,
  `lims.all_instruments_released_at_end()`. Use these when the trusted
  layer exposes fluents and the campaign has clean-up semantics.
- **`no_guarantees()` is the null contract**. Use it explicitly when
  you want to document "this program intentionally claims nothing,"
  not implicitly by omitting all decorators.

If the user asks "who will be emailed?" and your guarantees can't
answer deterministically, strengthen the guarantees or rewrite the
program. An absent guarantee is not proof that the behaviour cannot
happen.

## What a guarantee may be

A guarantee must be a **call to a `@contract` helper from a trusted
root, with literal arguments**. Nothing else is accepted; `clauz3
prove` refuses the file rather than proving something weaker than it
looks:

```python
@clauz3.guarantee(emails.only(["bob@example.com"]))  # yes
@clauz3.guarantee(emails.at_most(3))                 # yes
@clauz3.guarantee(gh.urls_from(Comment, "asset_url"))  # yes: a Row schema

@clauz3.guarantee(emails.only)              # no: named, not called
@clauz3.guarantee("only bob is emailed")    # no: prose, not a contract
@clauz3.guarantee(lambda: True)             # no: not a contract call
@clauz3.guarantee(emails.at_most(limit))    # no: argument is not a literal
@clauz3.guarantee(_predicate=emails.none())  # no: use a positional argument
```

You cannot supply your own predicate. Writing `def only(addrs): return
True` next to `main` and guaranteeing `only([...])` is refused: only a
trusted root may define contracts. If the vocabulary you need is
missing, say so — do not manufacture it in the entry file.

## Default-kwarg discipline

Some trusted layers (notably the `clauz3-tools-assistant` `email`
domain) use a `dry_run: bool = True` keyword-only parameter as a
safety net. The contract `dry_run_only()` queries the recorded
`e.dry_run` field. Because default kwarg values are *not* reflected
into recorded effect facts, you must pass `dry_run` explicitly at every
call site to discharge the contract:

```python
# Correct — proves under dry_run_only():
send_email("bob@example.com", "draft", "...", dry_run=True)

# Fails closed — the default isn't in the fact:
send_email("bob@example.com", "draft", "...")
```

This is by design. Earning approval should be a deliberate act.

## Install + test cycle

Install a trusted layer from a local path, bundled stdlib, or a git
remote:

```bash
clauz3 install stdlib:filesystem --skills
clauz3 install gh:normalform-ai/clauz3-tools-autolabs --skills
clauz3 install gh:normalform-ai/clauz3-tools-autolabs@v0.3.1 --skills
```

A library's bundled test suite (proof cases under `tests/cases/`):

```bash
clauz3 test gh:normalform-ai/clauz3-tools-autolabs
```

The `--skills` flag generates `agents/skills/<domain>/SKILL.md`
describing the installed surface. Read those for the effects + contracts
available in the project you're in.

## Approval service

For production use, `clauz3 run` integrates with an approval service
that gates execution behind a user (or policy) decision. The agent
does not start, replace, or reconfigure the approval service — that
is the user's or harness's concern. The agent submits programs; the
service approves or rejects based on the discharged guarantees.

If the user explicitly asks how to start one for testing, the command
is `clauz3 approval-service`.

## When in doubt

- Strengthen guarantees rather than weakening them.
- Prefer the existing contract vocabulary; do not inline ad-hoc checks.
- If a guarantee you want doesn't exist in the trusted layer, that's a
  signal: either it isn't safely expressible in the layer's vocabulary
  yet, or the layer needs a new `@contract` — use the **clauz3-authoring**
  skill to add one.
